## 一、改名：「开局科技」→「科技」

### 1.1 判据

**系统名 vs 时机描述，两回事。**「开局」在现状里有两种出现方式：

- **当系统名用**（「开局科技」＝这套系统的名字）⇒ **必须改**，否则读者会以为科技只在开局有，与用户 ① 冲突。
- **当时机描述用**（「开局随机获得一件白档道具」＝这条效果在开局那一下触发）⇒ **不改**，因为它说的就是事实，改了反而变假。

下面的逐处判断全部按这条判据走。**一个直接的推论**：`TECHS` 里所有 `desc` **一个字都不用改** —— 那 6 处带「开局」的文案（`二手教材` / `名师指点` / `孤注一掷` / `欧皇附体` / `预支未来` / 以及 `眼尖手快` 待重写）说的都是**效果何时触发**，不是系统名。

## 二、逐条平衡与智斗调整（59 条）

### 2.0 先立判据（否则 59 条会变成拍脑袋）

**什么算「智斗」**：这条科技让玩家在对局中**多做一次有意义的决策** —— 选时机（悔棋 / 天命在握 / 孤注一掷）、选目标（任意门 / 接收大员）、选顺序（双开 / 手速惊人 / 灵活就业）、读对手与局面（地产眼光 / 淘宝达人）、或**承担一个可计算的风险**（风险投资 / 闲不住 / 赌运加持）。
**纯数值进账（回合开始 +¥X、过起点 +¥X、事件卡 +¥X）不算智斗** —— 它们不给决策面。

**三档的智斗密度应当递增，这是定位不是缺陷**：

| 档 | 智斗重心 | 说明 |
|---|---|---|
| 白银 | **决策发生在「三选一」那一刻**（选稳钱还是选机制） | 一旦选定，之后是纯被动。这是白银「人人能用的稳收益」的另一面 |
| 黄金 | 使用中有**节奏 / 顺序**决策 | 悔棋 / 闲不住 / 灵活就业 / 手速惊人 |
| 钻石 | 重塑局面并**制造新决策**（对家也要重算） | 任意门 / 天命在握 / 接收大员 / 双开 |

**纯数值件为什么保留、为什么不把它改成智斗**：每档必须留够**稳收益锚**。若某档整档都是机制件，三选一会退化成抽签 ——
你会因为「这一张我一时看不出怎么用」而只能瞎选。**锚 ≠ 弱**，它的作用是把「机制件」的相对价值衬托出来。

**因此本批不做两件事**（明确写下来）：
1. **不为加智斗而新增交互窗 / 新增 RPC** —— 本批不扩协议面，中局科技卡才是引入新交互的正确时机。
2. **不做档位迁移**（见 §2.4：三条候选逐条评估后都不迁）。
3. **不把 pure-number 批量「智斗化」** —— 只修**明显超带 / 明显失效**的条目。

**改动汇总（59 条）：动效果 2 条（`眼尖手快` / `定期存款`）+ 待定 1 条（`金字招牌`）+ 不动 56 条。
一条 `desc` 都不因改名而改。**

### 2.4 档位归位评估：**三条候选，逐条评估后都不迁**

用户要求「品质与平衡性调整」，所以「该不该挪档」必须逐条给结论，不能绕过。

| 候选 | 拟迁向 | 结论 | 理由 |
|---|---|---|---|
| `心理素质`（白银 · 免查寝） | 迁去别的档？ | **不迁** | 它是**最弱**的一条，只能待在最低档。迁档不会让它变强，只会让它在池子里更显眼 —— 迁档解决不了「弱」，只有重定义能，而它「弱而无害」是白银该有的样子 |
| `定期存款`（黄金 · 利息） | 升钻石？ | **不迁，改数值** | 它确实**超出黄金带**，但根因是**利率定高了**，不是「这条该属钻石」。黄金已有 `复利`（钻石）当同族高档，把它升上去会让两条撞车。削数值（2% → 1.5%）比迁档干净得多 |
| `淘宝达人`（钻石 · 保底紫） | 降黄金？ | **不迁** | 对钻石档它偏弱，但①它**刚在批 2 改过口径**，此时再动会让交接书里的记录立刻过期；②降到黄金意味着钻石要补一件（本批不新增条目，见下）；③「保底一件紫」在后期（池窄、紫档被抽走时）反而变强 |

**为什么不新增条目去回补编号 4 / 6 / 17（白银）与 16（黄金）**：
控制侧已明确「各档数量相近当前已满足（20 / 19 / 20，极差 1）」⇒ **回补会把极差从 1 推到 2 甚至更大**，
且新条目要重新走一遍逐条定稿。本批**不新增、不删除任何条目**（`眼尖手快` 是**重定义**，不是新增）。

### 2.5 系统级调整 S1（可选 · 待定）：让池子避开「已被房主关掉的系统」

**问题**：科技池不按系统开关过滤。房主把**小卖部**关掉时，`学生折扣` / `会员卡` 是**死选**（100% 无收益）；
关掉**赌场**时，`赌场熟客` / `赌运加持` 同样是死选。这四条横跨白银与黄金，玩家在开局三选一里**看不出自己是死选**。

**建议（可选，需控制侧点头）**：给 `TechData.pool()` 加一个「本局已关闭的系统」排除参数（由 `_tech_phase()` 从 `_settings` 传入），
让小卖部关时排除那 2 条、赌场关时排除那 2 条。**代价很小**：`pool()` 多一个参数 + 调用处一句 + `tech_test` 一条断言；
**协议面零**（`s_tech_offer` 发的本来就是已过滤的候选名列表）。

**同类但**不**建议一起做**的**：`金字招牌`（依赖胜利条件 = 总资产排名）、`大器晚成`（依赖回合上限 ≥ 15）、
`预支未来`（依赖工资 > 0）—— 这三条是「**收益被设置削弱**」而非「归零」，且排除逻辑要读胜负设置 / 轮次常量，
判定口径不干净。**登记为已知项，不实现**（写进 `科技.md` 的「设置联动」一节）。

## 三、「游戏中获得」的结构口子（核心）

### 3.1 硬约束（侦察给出，本稿复核确认）

1. `p.tech` 是**单个 String** —— 一个玩家永远只能持有一条。
2. 唯一赋值处是 `_tech_phase()`；**全仓没有** `_grant_tech` / `_add_tech`。
3. `_has_tech` 是**单值相等**（`p.tech == name`）。
4. 快照 `players[].tech` 是**单个字符串**。
5. 玩家面板**只显示一行**「科技：<名>」+ 描述。
6. **没有中局获得的 UI**；现有两处科技界面（三选一弹层 / 定档横幅）标题都写死「开局科技」。
7. `_tech_tier` 是**全场单值**（不按玩家记档）。
8. `_tech_offers` / `_tech_open` 是**阶段态**，只服务开局三选一。
9. `implemented` 闸**只在 `pool()` 里** —— 按名直接发放会绕过它。
10. HUD 不展示科技（只有点开的玩家面板有）。

### 3.2 三个方案

#### 方案 A · 最小口子（只加一个发放函数，语义是「覆盖」）

- **改什么**：新增 `_grant_tech(p, name) -> bool`（房主侧）：查 `TechData.def(name)` 非空、
  `implemented` 为真、本局档位匹配（可选）→ 写 `p.tech = name` → 战报一条 → `_broadcast_state()`。
  数据形状 / 快照 / `_has_tech` / UI **全不动**。
- **代价**：**极小**。协议面 0；测试面 1 条；UI 面 0；56 处消费点 0。
- **它开出来的是真口子还是摆设？→ 「半真，且埋坑」**。函数会被调用、不是死代码；但「同时持有多条」仍**不可能**：
  第二条科技会把第一条**悄悄顶掉**，玩家看到的是「我明明选过 `点石成金`，怎么变成 `天选之人` 了」。
  ⇒ 这是**给未来的自己埋雷**，不是干净的口子。**不推荐。**

#### 方案 B · 真容器（**推荐**）

- **改什么**：
  - `_build_hp()` 里 `"tech": ""` → **`"techs": []`**（Array[String]）；`_tech_phase()` 的落地改成
    调 `_grant_tech()`。
  - `_has_tech(p, name)` **签名与语义不变**，实现改为 `return name in p.techs`。
    ⇒ **56 处调用点一行都不用改** —— 这是本方案最关键的性价比。
  - 新增 `_grant_tech(p, name) -> bool`：`TechData.def(name)` 非空 + `implemented` 为真 + **幂等去重**
    （已在则返回 `false`，战报「已持有」）→ 追加 → 战报 → `_broadcast_state()`。
  - 快照：`players[].tech` → **`players[].techs`（Array）**；顶层 `tech_tier` / `tech_open` 不变。
  - 玩家面板：单行 → **循环 N 行**（每行「名字」+ 其下小字描述，造型照现状；空列表整段不显）。
  - `_tech_phase()` 的「超时随机兜底」与「bot 立即定」照旧，只是落地走 `_grant_tech()`。
- **代价**：
  | 面 | 量 |
  |---|---|
  | 协议面 | **1 个字段改名 + 改类型**（`tech` → `techs`；`s_tech_offer` 的 `names`、`tech_tier`、`tech_open` 均不变），`联机协议.md` 两处条目同步 |
  | 测试面 | `tech_test` / `hud_test` / `item_test` 三套夹具与断言（`p.tech = "X"` → `p.techs = ["X"]`） |
  | UI 面 | 玩家面板一处（单行 → N 行） |
  | 那 56 处消费点 | **0**（`_has_tech` 实现换、签名不变） |
- **真口子 ✓**：容器**从第一天起就被真实使用** —— 现有开局三选一每局写进去的就是一个 1 元素列表。
  它不是「没人用的空字段」，而是「同一份数据的一般化」。将来的科技卡只需调 `_grant_tech`，
  **不必再动一次地基**。

#### 方案 C · 双字段兼容（`tech` 老字段保留 + 新增 `techs`）

- **改什么**：快照**新增** `techs`（全量），**保留** `tech`（= `techs` 首条）；内部只留 `techs`。
- **代价**：协议面**纯新增**（向后兼容）；测试面最小；UI 面 0（老面板照旧读 `tech`）。
- **它开出来的是真口子还是摆设？→ 真口子，但换来的是双份真相**：`tech` 与 `techs[0]` **必须永远同步**，
  这正是仓库反复踩过的「会烂的第二来源」（对照 `TIER_COLORS` 从 `game.gd` 挪到 `tech_data.gd` 的理由）。
  **不推荐** —— 省下的那点改动量（一个面板 + 三套测试）不值一条永久性的同步义务。

> **推荐：方案 B。** 一句话理由：**它让「科技可以有多条」成为数据形状上的事实，而代价只是改一个快照字段名
> 与三套测试夹具 —— `_has_tech` 的 56 处调用点与全部效果逻辑一行不改。**
> 用户「担心引入用不到的复杂度」的那条顾虑，在 B 里不成立：容器每局都在跑，不是空字段。

### 3.3 必须回答的四个问题

**① 重复获得同一条科技怎么办？→ 幂等（不叠加），备选「折现」**
- **推荐**：`_grant_tech` 遇已持有 ⇒ 返回 `false`、战报「已持有 `X`，不再重复发放」，**不做任何数值补偿**。
  理由：科技里有一批**计数器型**（`厄运保单` 4 次 / `天命在握` 4 次 / `任意门` 2 次 / `悔棋` 1 次 /
  `东山再起` 1 次 / `接收大员` 1 次）。若允许叠加，就必须**逐条**定义「可叠加 / 不可叠加」——
  **在没有科技卡的今天，那是凭空发明规则**。幂等是唯一**不需要逐条拍板**、且最符合直觉的规则。
- **备选 B（将来要「重复也有收益」时）**：重复时**按档折现**一笔现金（`TECH_DUP_CASH := {白银 1000, 黄金 3000, 钻石 8000}`）。
  比「叠加」安全、可测、不需要逐条定标。**本批不实现。**

**② 「已获得科技」在玩家面板里怎么展示？**
- 现状：`player_popup.gd` 单行「科技：`<名>`」+ 其下小字 desc，仅在「存活且非空」时显示。
- 方案 B 之后：**同一个造型，循环 N 次**（每条一行名字 + 其下描述小字）；空列表整段不显、出局者整段不显
  （两条既有口径都保留）；换行宽度照该面板既有的「可用宽度 = 面板宽 − 内边距 ×2」口径。
- **待定**：条数多了怎么排（换行堆叠 / 折叠 / 滚动）。当前最多只能有 1 条，**本批不预设**；
  等科技卡落地时按实际条数（预计 1~3）再定。

**③ 中局获得时，「定档」这条还成立吗？→ 建议保留定档，改「按档发」；备选「按条发」**
- **定档的本意**是给**开局三选一**一把尺（保证三个候选同强度，别让「抽到白银 vs 抽到钻石」变成开局运气）。
- **推荐（保留定档 / 按档发）**：中局发的科技也取自**本局那一档**（`pool(_tech_tier, …)`）。
  好处：①「本局科技等级」仍是**全场共识**，UI 不用新增档位选择；②稀有度仍有档位锚；
  ③ 与既有口径一致 —— 这正是 `术语表.md` 已记的「畸变总开关为关时畸变卡那一档作废、5% 并入机会卡」的同一条思路：
  **没定档（`tech_on = false`）时不生成科技卡**。
- **备选（按条发 / 卡面自带档位）**：更像道具卡，惊喜感更强；但会**打散「本局同档」这条已定稿机制**，
  且中局发一条钻石科技在白银局里是**强度断层**。若采用，须把 `科技.md` 的「全员同档」改写为
  「**三选一那三张同档**（只约束发车前那一步）」，属**口径降级**，要显式记进 `设计决策留痕.md`。
- **本批不拍**：无论选哪条，都只影响 `_tech_tier` 的**消费方式**，不影响 §三 的结构改动。

**④ 中局发放需要新 RPC 吗？**
- **数据面：不需要。** `_broadcast_state()` 的 `players[].techs` 一改，客户端就能看到「谁获得了什么」。
- **表现面：需要一条广播**（若要「获得一条科技」的揭示演出，像畸变卡 / 道具卡那样的 `DeckReveal` 弹层）。
  可**复用既有的抽卡演出通道**，不必新造机制。**本批不做**（没有科技卡就没有触发点），只把这条写进 `科技.md`。

### 3.4 **同档内的覆盖 / 叠加规则（本批只写文档，不写代码）**

方案 B 之后「多条共存」**在结构上可能**，但**在对局上仍不可达**（唯一发放路径 = 开局三选一，恰好发 1 条）。
所以下面这张表**本批只落进 `科技.md`**，代码不动 —— 但必须现在写，否则将来加卡的人要重新推一遍。

**因为定档是「全场同档」，跨档组合（如 `富二代` 钻石 + `助学金` 白银）天然不可能**，同档组合很少：

| 档 | 组合 | 规则 |
|---|---|---|
| 钻石 | `富二代`（起始资金 ×2） + `预支未来`（+¥30000） | **顺序待定**：建议「先 ×2、再 +30000」（乘算在前，加算在后，与道具侧 `招财猫 → 保安巡逻` 的「先加后乘」口径**相反**，须显式写明） |
| 钻石 | `双开`（每回合 2 件） + `熟能生巧`（不冷却） | **独立叠加**（一个管件数、一个管冷却） |
| 黄金 | `灵活就业`（首件 −1⚡） + `手速惊人`（冷却 −1） | **独立叠加** |
| 黄金 | `地产眼光`（前 2 块半价） + `批发拿地`（−25%） | **已有定稿**（乘算叠加） |
| 跨档（备选「按条发」时才可能） | `摸鱼时刻`（转 0 +¥500） ↔ `闲不住`（转 0 改前进 2，"不再算掷出 0"） | **覆盖**：`闲不住` 生效时 `摸鱼时刻` 不触发（现状 desc 已写明） |
| 跨档 | `熟能生巧`（钻石） ↔ `手速惊人`（黄金） | **覆盖**：不冷却压倒「冷却 −1」 |
| 跨档 | `预支未来`（不再领工资） ↔ `工资上调` / `金饭碗` / `校园卡`（道具） | **覆盖**：工资类加成**一并作废**（现状 desc 只说「经过起点不再领工资」，**没说是否连加成一并作废** —— 这是**新暴露的口径空洞**，须在 `科技.md` 补写） |

## 六、实现风险

按「动了会不会漏」排序，**前 3 条是本稿重点**。

### 1. 结构改动（方案 B）——本批唯一会碰 `game.gd` 与协议的东西

- **牵动**：`_build_hp`（初始字段）、`_tech_phase`（落地改走 `_grant_tech`）、`_has_tech`（实现）、
  `_broadcast_state`（快照）、`_open_player_popup` + `player_popup.gd`（面板）、`联机协议.md` 两处。
- **要动什么**：见 §3.5 的 B1~B9。
- **最大的漏**：**快照字段改名后，客户端读的键名漏改一处** ⇒ 面板永远显示空。
  这个坑仓库**踩过**（「曾漏发 `shop_peer` 导致小卖部界面永不显示」）。
  ⇒ 实现后必须**真跑一局联机回归**（`--autotest=host` + client 同一条命令），不能只跑单测。

  `_mk_player`、`hud_test` 的状态构造）没跟着改 ⇒ 用 `p.tech` 写进去、`_has_tech` 读 `p.techs` ⇒ **静默失效**

  ⇒ 建议给 `_has_tech` 加一句**兼容读取**（`p.get("techs", [])`，且若 `p` 里出现旧的 `tech` 字符串则视为一条），
  只在迁移期保留，或干脆**全仓搜 `\.tech\b`** 逐个改净。

### 2. 三选一 / 定档演出 / 那 56 处消费点

  ⇒ 实现前先 **`grep "\.tech"` 全仓过一遍**，把「直读 `p.tech`」的每一处都改成 `_has_tech` 或 `techs`。
