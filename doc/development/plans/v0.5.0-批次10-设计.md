# v0.5.0 批次 10 设计：棋盘放大（几何优化）

> 状态：**设计（待评审）** ｜ 立项 2026-10-04 ｜ 范围：**③ 的前半（A）**
> 上级：用户需求五条。③ 经确认**拆两批**：批次 9 = (B)（已完成）、**批次 10 = (A)（本文）**、
> 批次 11 = ⑤ 小人与房子立体。
> 用户选择：**A —— 只做几何优化**（不做"3D 拉近看局部"，也不改字号 / 不裁棋盘 / 不抬画布分辨率）。

## 1. 目标

让**棋盘在桌垫/木桌上占比更大、两端的格内文字更大**，幅度**约 +12~15%**（格内文字 ~11px → ~13px）。

用户原话：`③棋盘在桌面的比例加大一点，现在不管是2D还是3D视角，都字太小了`。

## 2. 可行空间（先说清上限，免得把"做不到的"当"没做好"）

推导得到一条恒等式（**别凭直觉**）：

> **棋盘的屏幕大小 = `TABLE_W`(8 世界) × ①棋盘占桌垫的比例 × ②桌垫占屏宽的比例**

- ① 现为 **91%**（`MAT_MX/MT/MB` = 100/100/260 是桌垫围着棋盘的那圈留白；`MAT_MX=0` 时可到
  2016/2016 = 100%）⇒ 上限 **+9.9%**。
- ② 现为**约 94.5%**（取景断言只给整条轨道留了"最小 10.9px @ wt≈0.45、两端约 35px"的余量）⇒
  上限 **约 +6%**。
- ⇒ 两者相乘，**几何优化的硬上限约 +15%**。要明显更大只能放弃"整块棋盘同时入画"
  （用户已明确**不做**那一档）。
- ⚠ **上面 ② 这个上限估计已被实测取代（2026-10-04，本批落地后）**：② 引的 94.5% 是"批次 5
  之前"那一版的余量，而 **T1 把桌垫裁浅（进深 6.152 → 5.626）反而松了取景余量** ⇒ T2 实测拿到
  **+12.9%（2D）/ +9.0%（3D）**（2D 端超出这里估的 ~+6%）。⇒ **"≈ +15% 的合成上限"不成立**；
  本批净收益 ≈ **+15%（3D）/ +19%（2D）** = 几何 +5.7% × 相机 +9.0%/+12.9%
  （见 `game-design/设计决策留痕.md` §十）。

因此本批**只动三样**：桌垫留白、木纹框宽、相机远近。**不动** `TILE` / 字号 / `VP_SIZE` /
棋盘的 18×12 格数 / `WORLD`（这些一改就是另一件事，且不带来屏幕尺寸收益——已推导过：
整体等比放大画布与窗口会**完全抵消**）。

## 3. 顺带理清一条**互相矛盾**的旧说法（必须定案）

- `layout_test` 的取景断言量的是**桌垫四角**（`TABLE_SIZE`），并在注释里明确论证了
  "**木纹是"桌子本身"，第一人称下桌子伸出画面是自然的；要全程入画的是看得见的棋面（桌垫）**"。
- 但 `table_3d.CAM_DIST` 那段注释说取景断言"**按木桌四角量**（±5.2 / ±4.28）"，还说
  "21 档最紧的一档余量 93.4px" —— 与"桌垫最紧 10.9px"**对不上**（木桌在桌垫之外，
  余量不可能比桌垫更大）。⇒ **`CAM_DIST` 那段是过期的**。

**定案：取景判据 = 桌垫四角**（保持 `layout_test` 的现状，它是刻意的、且理由成立）。
本批把 `CAM_DIST` 那段注释**改准**（写"按桌垫四角量"、并更新为实测值），不再声称木桌。
⇒ 木纹框可以**收窄**到只剩"桌子边"的观感作用，不必再为它留取景预算。

## 4. 设计

### 4.1 桌垫留白（①）

`board_view.gd`：`MAT_MX` / `MAT_MT` / `MAT_MB`（现 100 / 100 / 260）。
- **底边留白可以收得最狠**：它原本是"玩家面前"那条（批次 7 的牌垫阶段按钮已退场、手牌也早就
  搬到**木纹**上了）⇒ 今天只剩观感。
- **留一点边**：桌垫外圈仍要看得见一圈"布边"（`MAT_*` = 0 时格子会顶到桌垫边缘，木纹直接贴着
  格子的描边，观感上"棋盘没有垫子"）。**建议初值 40 / 40 / 90**，再对着出图微调。
  （三个值一起缩，别只缩一个 —— 那会让棋盘在桌垫里偏到一边。）
- 连带：`MAT_RECT` 自动跟着变（它由这三个数 + `BOARD_OFFSET` + `WORLD` 派生）。

### 4.2 木纹框（观感 + 让相机有余量）

`table_3d.gd`：`WOOD_FRAME` 1.2 → **0.7** 左右。它只是"桌垫之外那一圈木桌"的宽度。
**注意**：它会牵动**台灯底座的位置**（台灯坐在木纹带上，见 §4.5）。

### 4.3 贴图窗口（**改桌垫必须一起改**）

`table_3d.TEX_WINDOW_PX`：必须与新的 `MAT_RECT` **同比例 + 画布正中**，且
`MAT_WINDOW_W`（2020）保持不变（它是"桌垫铺成多宽画布"的口径，两边同源）。
`layout_test` 有断言钉住"窗口比例 == 桌垫比例且居中"——**它是安全网，不是要改的东西**：
改完 `MAT_*` 之后按新比例重算 `TEX_WINDOW_PX` 即可（`size = (2020, 2020 × MAT_RECT.h/MAT_RECT.w)`、
`position = ((2048-2020)/2, (2048-size.y)/2)`）。
- 连带：`TABLE_D = TABLE_W × 窗口高/窗口宽` 自动变（**桌面进深变浅**，桌子更"扁"）。
- 连带：`table_mat.uv1_scale/offset` **不需要手改**（它们由 `TEX_WINDOW_PX` 与 `VP_SIZE` 派生）。

### 4.4 相机（②）

`table_3d.gd`：`CAM_DIST`（现 5.2）与 `VIEW_DIST_2D`（现 8.6）**一起**收，直到
`layout_test` 的"整条轨道 21 档余量 > 5px"逼近下限（**夹值**，不是猜）。
- **两条一起收**：`VIEW_DIST_2D` 单收会让"两端面积比"这条（须在 [0.6,1.6]）漂开。
- `CAM_TILT_DEG`（50）/ `CAM_TILT_2D_DEG`（88）/ `CAM_FOV`（55）**不动** ——
  俯角是观感契约（"第一人称 50°"），FOV 收了会同时收紧取景、把收益抵消掉（已推导）。
- 建议**先按 +10% 收**（`CAM_DIST` ≈ 4.7、`VIEW_DIST_2D` ≈ 7.8），再按余量与出图微调。

### 4.5 台灯与手牌：两处**必须重取**的画布/世界常量

- **`LAMP_BASE`**（现 `Vector3(-4.9, 0.0, 1.0)`，坐在木纹带上）：
  `WOOD_FRAME` 收到 0.7 后木桌外沿 = `TABLE_W/2 + WOOD_FRAME` = **4.7** ⇒ 现值 -4.9 会让底座
  **悬空到桌外**。改成 ≈ **-4.35**（仍在桌垫之外、木纹带之内），并复核：
  `layout_test` 的「灯杆 / 灯罩 / 光源都不在桌垫窗口内」「3D 端看得见台灯」「灯罩投影不落在棋盘上」
  三条断言 + 底座外缘不越木桌外沿（`|x| + 底座半径 ≤ TABLE_W/2 + WOOD_FRAME`）。
  **注意相机推近是第二条理由**：台灯在画面左侧、位置本就贴边（原推导里"z 一到 2.6 上下 |x|=4.2
  就出左沿"），相机一近，左侧被裁得更多 ⇒ 台灯可能需要**再往桌心/近端挪一点**，
  或把杆高/臂长一起微调。**以「3D 端看得见台灯」那条断言 + 出图为判据**。
- **`HAND_BASE_PX`**（现 `Vector2(1009.0, 1862.0)`，画布像素）：它是**画布常量**，而桌垫一缩、
  `fit_zoom` 就变 ⇒ 同一个画布像素会落到**另一个桌垫相对位置**。必须重取，使手牌整排仍落在
  **木纹留白上**（桌垫之外、木桌之内、不压棋盘、不被画布边缘裁掉）——
  `layout_test` 那一族的 5 条断言（在木纹上 / 在木桌内 / 不陷桌 / 未被画布裁 / 比棋盘更靠自己）
  就是它的判据。

### 4.6 常量注释里的**实测数字**要重取

本批改的常量注释里写满了实测值（`CAM_DIST` 的 21 档余量与面积比、`MAT_MB` 段的留白理由、
`TEX_WINDOW_PX` 的比例推导、`HAND_BASE_PX` 的换算口径、`LAMP_BASE` 的三条尺子…）。
**改了值就必须把那些数字重新量、重新写** —— 否则注释立刻变成假话（本仓库反复栽在这上面）。
`layout_test` 的日志里已打印余量 / 面积比 / 实测包围盒，直接用那些数。

## 6. 验收

1. `load_all` + 全量套件全绿、`SCRIPT ERROR` 0。
2. `layout_test` 的取景族全绿：**21 档余量 > 5px**、**两端面积比 ∈ [0.6,1.6]**、
   窗口比例==桌垫比例且居中、手牌 5 条、台灯 3 条。
3. **新增一条可执行断言：格子的屏幕宽度**（把某格四角经 `camera.unproject_position` 投到屏幕、
   取包围盒宽）**必须 ≥ 一个下限**（建议先按现状量出基线 ~63px，再把下限钉在 **70px**）——
   否则本批的"字更大"只是"看着像"，没有任何东西拦得住它回退。
4. **出图对比**（真实窗口）：同一取景下的**批次 9 图 vs 本批图**（`--shot=…table_plain.png`），
   棋盘明显更大、木纹边更薄、台灯位置正常；2D 端（`view2d`）同样。
5. **帧率实测**（`--fps=N`）：桌面画布尺寸没变（`VP_SIZE` 未动）⇒ 预期无变化，但本批改了取景
   与木纹，**实测一次并记数**（设计稿 §八 风险 1 的口径）。
6. 单人试玩：两端看棋盘的字比之前大、棋盘没有超出桌垫、手牌仍在木纹上、点得到格子。

## 7. 不变量与风险

- **不变量**：玩法逻辑 / 数值 / `@rpc` / `s_state` 字段 / 哨兵 / 新增素材（`LICENSE`）；
  `VP_SIZE`、`MAT_WINDOW_W`、牌与格子的**画布尺度**（`TILE` / 字号）一律不动。
- 风险一：**`TEX_WINDOW_PX` 与 `MAT_RECT` 必须同时改** —— 只改一边会让"看到的"与"点到的"脱钩
  （批次 5 Task 2 真踩过；`layout_test` 那条跨类一致性断言就是为它留的）。
- 风险二：`HAND_BASE_PX` 是**画布常量**，桌垫一缩它就会相对桌垫漂走（同上一条的同一类坑）。
- 风险三：`LAMP_BASE` 忘了跟着 `WOOD_FRAME` 走 ⇒ 底座悬空到桌外。
  （**更正（批次 10 Task 1 审查）**：本条初稿写"断言只查'不在桌垫内'、不查'在木桌内'"——**这是错的**：
  `layout_test` 里批次 6 的 `in_table` + `base_gap` 两条**本来就查了**木桌外沿（x 与 z 都查，
  连灯罩一起；判据 `|x| + bottom_radius ≤ TABLE_W*0.5 + WOOD_FRAME`）。所以**不需要新补断言**，
  只需按 §4.5 核一遍实测值。实现者正是这么做的。）
- 风险四：改了常量却不改注释里的实测数字 ⇒ 注释变假话（本仓库的反复教训）。
